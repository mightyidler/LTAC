# DHCP IP 변경 자동 복구 — 최종 구현 가능성 검토

검토일: 2026-10-18, Asia/Seoul.

## 판정

**최초 페어링과 네트워크 깨우기 설정을 마친 LG TV가 같은 로컬 네트워크에서 DHCP 주소만 변경하는 경우, 고정 IP나 DHCP 예약 없이 자동 전원 제어를 복구하는 기능은 구현 가능하다. 현재 LTAC이 모든 경로에서 이를 완성했고 실기 검증까지 마쳤다는 판정은 아니다.**

주소 변경 직후 재발견·재인증에 시간이 필요하다. 무중단이나 모든 순간의 전원 명령 성공을 보장할 수는 없다. 특히 Windows 종료/절전의 짧은 OFF 예산과 IP 변경이 겹치면, 그 시간 안에 새 주소를 찾지 못할 수 있다.

## 프로토콜 근거

1. Wake-on-LAN은 MAC을 담은 매직 패킷을 로컬망에 브로드캐스트할 수 있다. 깨우기 자체에 TV의 현재 IP를 알 필요는 없다. 호스트 주소는 상태 확인에 별도로 사용된다. [Home Assistant WoL 문서](https://www.home-assistant.io/integrations/wake_on_lan/)
2. LG Connect SDK는 `urn:lge-com:service:webos-second-screen:1`을 SSDP 검색 대상으로 사용한다. LTAC도 같은 서비스 식별자로 TV의 현재 주소와 설명을 얻는다. [LG Connect SDK 소스](https://github.com/ConnectSDK/Connect-SDK-iOS-Core/blob/master/Services/WebOSTVService.m)
3. UPnP UDN은 특정 기기에서 시간과 재부팅을 거쳐 유지되는 식별자다. IP가 변경되면 기기는 자신의 서비스를 다시 광고하도록 규정되어 있다. 따라서 IP와 기기 신원을 분리할 수 있다. UDN은 탐색용이며 인증을 대체하지 않는다. [UPnP Device Architecture 2.0, 문서 인쇄 쪽 32·51](https://openconnectivity.org/upnp-specs/UPnP-arch-DeviceArchitecture-v2.0-20200417.pdf)
4. 새 주소에서도 저장한 인증 키와 TLS 지문을 검증한 후 제어한다. 인증 정보 자체가 취소되거나 바뀐 경우는 IP 변경과 별개이며 재승인이 필요할 수 있다.

## 확인한 증거와 범위

| 검증 | 결과 | 증명하는 범위 |
| --- | --- | --- |
| 이번 `cargo test --all-targets` | 25개 통과 | 로컬 프로토콜, WoL 패킷, 상태 전이, DPAPI 등 기존 테스트 범위 |
| 기존 실제 C4 SSDP 연결 및 OFF/ON | 성공 기록 존재 | 해당 TV에서 검색·저장 인증·네트워크 깨우기가 동작함 |
| 기존 저장 IP 오류 재현 | 실제 TV를 재발견·인증하고 설정 사본의 IP 복구 성공 기록 존재 | 오래된 저장 주소에서 복구할 수 있음. 실제 DHCP 변경 시험은 아님 |
| 이번 현재 코드로 재검색 | 실패: 저장한 TV를 로컬망에서 찾지 못함 | 현재 시점의 실제 성공을 확인하지 못함. TV 전원/접속 상태 원인은 확정하지 않음 |
| 이번 기존 주소 TCP 3001 접속 확인 | 1.5초 내 접속 미완료 | 기존 주소에서 제어 서비스 응답도 확인되지 않음 |
| 실제 DHCP 주소 재할당 후 ON/OFF 반복 | 미실행 | 제품의 최종 실기 합격 판정은 아직 불가 |
| 로그인 전 서비스의 주소 변경 후 전원 제어 | 실기 미검증 | 사용자 세션의 과거 성공 기록으로 대체하지 않음 |

기존 근거는 [VALIDATION.md](VALIDATION.md)와 [주소 복구 기록](evidence/address-recovery-2026-10-18.jsonl)을 참조한다. 이번 재검색 결과는 [별도 기록](evidence/ip-recovery-final-probe-2026-10-18.jsonl)에 저장했다. 실패 뒤의 반례·메모리 복구 단계는 실행되지 않았으므로 이번 성공 항목으로 계산하지 않는다.

이번 검증용 [예제](../examples/verify_ip_recovery.rs)는 원래 설정을 수정하지 않고 임시 설정에만 잘못된 IP를 넣는다. 실제 TV에는 검색·인증·상태 조회만 수행하며 WoL, ON/OFF 명령, 페어링 승인 요청, 공유기/DHCP 변경을 수행하지 않는다. `cargo run --example verify_ip_recovery`로 재현할 수 있다.

## 제품 코드에서 필요한 보완

| 위치 | 현재 동작 | 필요한 보완 |
| --- | --- | --- |
| `src/controller.rs`, `wake_session_inner` | 재시도 가능한 접속 오류의 경우 두 번째 시도에만 재검색 | TV 부팅·DHCP 준비 지연을 고려해 전체 시간 예산 안에서 검색을 간격 두고 반복 |
| `src/controller.rs`, `paired_session` 및 `src/service.rs` | 복구 결과에서 Session만 반환. 서비스 설정은 저장 경로가 없고 호출 측의 Config도 갱신하지 않음 | 인증한 새 주소·인터페이스 정보를 서비스의 현재 설정에 유지. 사용자/서비스 암호화 설정을 서로 덮어쓰지 않음 |
| `src/connection.rs`, `recover` | MAC 조회가 일시 실패해도 `None`으로 덮어쓰고 깨우기 검증 상태를 해제 | 같은 인터페이스라는 근거가 유지되면 마지막 정상 MAC을 보존. 실제 연결 방식 변경과 조회 실패를 구분 |
| `src/service.rs`, OFF 및 `src/sync.rs`, OFF | 캐시 연결이 존재하면 사용. 해당 작업에서 캐시 실패 후 재접속 경로가 없음 | OFF가 전송되기 전 실패했다면 남은 예산 내 복구. 전송 여부가 모호하면 중복 전송 여부를 증거에 따라 판단 |
| `src/wol.rs` | 송신 경로와 브로드캐스트에 저장한 주소 정보를 사용 | PC 인터페이스/서브넷이 바뀐 경우 현재 LAN 기준으로 재선정. TV IP만 바뀌고 LAN이 같으면 기존 브로드캐스트 사용 가능 |
| `src/connection.rs`, 수동 IP 연결 | 발견 식별 정보를 저장하지 않음 | 수동 연결 사용자에게도 가능할 때 인증된 TV와 발견 정보를 연결하여 자동 복구 기반 확보 |

PC의 `NotifyIpInterfaceChange` 알림만으로 TV의 DHCP 변경을 모두 감지할 수는 없다. TV 연결 단절과 제어 실패 시에도 복구해야 하며, 필요하면 SSDP 광고를 수신한다. 광고 수신은 상시 상태 조회와 다르지만 UDP 특성상 광고 수신만으로도 충분하지 않으므로 실패 시 능동 검색을 함께 사용한다.

## 구현 후 실기 합격 기준

- 같은 LAN에서 TV의 실제 DHCP 주소를 변경하고, 추가 승인·IP 입력 없이 새 주소 인증 및 OFF/ON 확인.
- TV 대기 중 DHCP 임대가 바뀌는 조건에서 저장 MAC으로 깨운 후 새 IP를 찾는지 확인.
- TV의 검색/제어 서비스가 늦게 준비되어도 제한 시간 안에 재시도로 복구되는지 확인.
- 이전 IP를 다른 장치가 사용해도 그 장치에 잘못된 제어를 하지 않는지 확인.
- 복구한 주소가 후속 명령과 서비스 재시작 뒤에도 적절히 재사용되거나 다시 복구되는지 확인.
- IP 변경 직후의 종료/절전 OFF는 별도 시간 제한 시험으로 확인하고, 성공하지 못한 경우를 성공으로 표시하지 않음.

TV가 네트워크 깨우기를 지원/허용하고, PC와 TV가 서로 검색·통신할 수 있어야 한다. 전원 분리, 네트워크 대기 단절, 검색/브로드캐스트 차단, 인증 초기화, 하드웨어/연결 방식 변경까지 IP 변경 복구만으로 해결된다고 보장하지 않는다.
